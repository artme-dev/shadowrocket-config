# Итог настройки Shadowrocket: VPN → ISP

Состояние на 4 ноября 2026, Asia/Novosibirsk. Финальный профиль опубликован,
проверен нативно на Mac и принят пользователем на iPhone. После повторного
добавления ссылки на Mac пользователь также подтвердил работоспособность.
Это точка входа в опыт сессии; подробные измерения сохраняются в журналах по датам.

## Цель и окончательная схема

Стабильный выходной IP для OpenAI и Claude при смене входного VPN, управление
из файлов и одна персональная ссылка для устройств Shadowrocket. Обычный трафик
использует VPN без ISP; существующие DIRECT-исключения сохранены. Это последнее
согласованное решение: ранний вариант «весь PROXY через ISP» отменён.

```text
                         ┌─ OPENAI → ISP-OPENAI ─┐
Правила Shadowrocket ────┤                     ├─ родитель artem-personal
                         └─ CLAUDE → ISP-CLAUDE ─┘            │
                                                        AUTO / вручную
Физически для AI: устройство → выбранный вход VPN → IPRoyal → сервис
Для OTHER:        устройство → выбранный вход VPN → сайт
Для DIRECT:       устройство → сайт
```

Два AI-выхода независимы по настройке, хотя сейчас используют один IPRoyal
Multi-device с выбранным пользователем доступом на четыре источника. Изменение
входного VPN не должно менять ISP-IP. При отказе ISP или отсутствующем родителе
AI-соединение прекращается: запасного DIRECT/VPN с иным IP в AI-группах нет.

`SERVICE` — группа просмотра/выбора сервисных узлов, правила к ней не обращаются.
Выбор внутри SERVICE не переключает OPENAI или CLAUDE. `artem-personal` управляет
входным VPN. В Home одна персональная подписка с префиксами `VPN-*` и `ISP-*`;
группы политик не создают отдельные заголовки подписок в Home. Это принятое
пользователем устройство интерфейса.

Семейная подписка `artem-public` содержит только серверы и распространяется
отдельно. Персональный полный файл содержит серверы, правила, выходы и цепочки.

## Почему именно этот пул

Приоритет — баланс AI и обычного VPN. На первом этапе рассмотрены 34 варианта:
короткие HTTPS-пробы, повторные проверки финалистов и загрузки по 2 MB. Затем
свежие параметры окончательных десяти проверены в самом Shadowrocket: TCP,
ожидаемый ISP-IP и UDP через ISP. Предварительный успех в sing-box сам по себе
не считался подтверждением нативного клиента.

| Порядок AUTO | Вход | Основание |
|---|---|---|
| 1 | Xeovo Netherlands, Shadowsocks AEAD | Хорошие короткие пробы задержки/скорости, нативные TCP и UDP через ISP |
| 2 | Xeovo Germany, Trojan TLS | Рабочая цепочка и дополнительный протокол подключения |
| 3 | Xeovo New York, VLESS WebSocket | Ранее подтверждённая цепочка и голосовой UDP; повторная проверка ISP |
| 4 | Xeovo Sweden, VLESS WebSocket | Прошёл отбор и нативную цепочку |
| 5–9 | Blanc Amsterdam, Frankfurt, Zurich, Almaty, Oulu | Пять разных адресов входа, успешные нативные TCP/UDP через ISP |
| 10 | Xeovo Singapore, VLESS WebSocket | Рабочий, но более медленный географический резерв |

В снимке 50 узлов Blanc было лишь шесть разных сочетаний server:port. Несколько
названий городов могли означать один вход, поэтому не набирали только разные
названия. Пять разных адресов не доказывают независимость инфраструктуры.

Hysteria2 Netherlands/Germany первоначально выглядели перспективно. Но в
контролируемой нативной проверке UDP через ISP они давали таймауты, тогда как
New York WS с тем же STUN-адресом отвечал. Netherlands HY2 напрямую также
отвечал. Точная причина внутри клиента не установлена; эти HY2 исключены из
общего AI-пула и заменены проверенными SS/Trojan. Это вывод о проверенной
комбинации, а не о протоколе вообще.

AUTO — fallback по приоритету, не случайный ротейт и не соревнование скорости.
Проверка раз в 120 секунд, timeout 5 секунд, URL gstatic generate_204. Она оценивает
доступность входа, а не всю цепочку до ISP. Если вход жив, но ISP через него
не работает, может потребоваться ручной выбор другого входа. Переключение не
обещает сохранения уже открытых TCP/голосовых сессий.

## Что действительно доказано

| Утверждение | Доказательство и граница |
|---|---|
| Все 10 входов подходят для текущей ISP-цепочки | Нативные TCP, HTTPS-проверка ISP-IP и не менее двух успешных UDP-проб для каждого |
| Полный финальный профиль работает на Mac | Импорт/компиляция 2.2.93 build3488, четыре IP-маршрута и 2/2 UDP через ISP; затем пользовательский повторный импорт |
| Профиль переносится на iPhone | Ранее телефонные логи подтверждали группу-родителя и голосовой UDP; после финальной публикации пользователь принял профиль по чек-листу |
| Отказ ISP не меняет AI-IP | Моделируемый отказ в изолированном нативном профиле остановил запрос |
| Отсутствующий родитель не обходится | Явная ошибка строгой цепочки при close-if-proxy-chain-missing=true |
| AUTO выбирает резерв | При первом недоступном входе выбран Blanc; первый запрос упал, два последующих получили прежний ISP-IP |
| Опубликован именно проверенный файл | API и raw main/alias совпали побайтно с локальной сборкой |

Пользовательская приёмка финального профиля не сопровождалась новым подробным
телефонным логом или отдельными значениями каждой пробы. Не приписывать ей
измерение потерь, jitter, многодневную стабильность или проверку всех сетей.

Релиз: 10 входов, 2 ISP-выхода, 6 групп, 507 правил, 402 голосовых префикса.

`adf3f4d2bf949f0f8bb719c00ddc9823e281d8e46fc176a094bff5adf5029f65`.

## Ошибки, которые не надо повторять

1. **Не выпускать полный профиль до нативной проверки.** Первый полный файл
   оказался неработоспособным из-за цепочки. Сначала отдельная копия, затем
   проверка маршрутов и только потом обновление основной ссылки.
2. **Не переносить синтаксис другого клиента буквально.** Для проверенного Xeovo
   WS нужен нативный obfs-uri; path игнорировался. underlying-proxy не заменял
   подтверждённый Proxy Pass. Успех sing-box не доказывал работу Shadowrocket.
3. **Учитывать версию и работающий процесс.** На старом Mac 2.2.69 цепочка через
   группу не работала; после обновления 2.2.93 подтверждена. Версию проверяли и
   у приложения, и в журнале PacketTunnel.
4. **Избегать одинаковых имён экспериментальных узлов.** Общий реестр серверов
   клиента и старые профили искажали ранние результаты. Префикс AR-* дополнительно
   интерпретировался интерфейсом как страна; финальный префикс — VPN-*.
5. **Не считать открывшийся ChatGPT доказательством пути голоса.** Голосовые
   соединения к literal IP обходили ранние доменные правила. Нужны официальные
   голосовые сети, приоритет правил и отдельные UDP-пробы/журнал.
6. **Сначала исключать локальный фильтр UDP.** Disable STUN блокировал пробы до
   отправки в цепочку. По таким таймаутам нельзя заключать, что ISP не умеет UDP.
7. **Не отключать рабочую связь ради тестов.** Сохранять профиль для отката,
   тестировать точечные маршруты, не включать watcher/kill switch и не выключать
   или перезапускать VPN без отдельного согласования.
8. **Сохранять плохие результаты и время.** Один замер скорости не описывает опыт
   использования; повторно экспортированный файл лога с тем же именем может
   содержать новые записи. Проверять содержимое, диапазон времени и hash.

## UDP, голос, производительность и источники IPRoyal

Выданный тестовый Proxy-Seller ISP отвергал UDP ASSOCIATE кодом 7. Это относится
к конкретному продукту/доступу; не переносить вывод на все продукты провайдера.
Текущий IPRoyal прошёл реальные UDP-пробы, поэтому выбран для голосовых сценариев.

На Mac Disable STUN после временно разрешённых сравнений восстановлен во
включённое состояние. Эта глобальная настройка не приезжает с конфигом и может
мешать голосу. Её постоянное отключение не согласовано. Для проверки общего UDP
использовали Quad9 9.9.9.9:9953, TXT proto.on.quad9.net → do53-udp, не меняя
системный DNS. Узкое правило AND адрес+порт направляет эту пробу в OPENAI.
DNS-ответ не показывает выходной IP: его проверяли отдельно по HTTPS и политике.

Короткие пробы по 2 MB: Netherlands SS — около 21.6 Mbps через VPN и 16.7 через ISP;
Germany Trojan — 17.1 и 16.7Mbps. В более ранней серии 100 MB были и хорошие
результаты, и серьёзный выброс: 5 MB за 91 секунду. Это не доказательство устойчивой
скорости. Upload, длительные потери/jitter и работа под нагрузкой систематически
не измерены; пользовательский опыт важнее одного числа speed test.

IPRoyal учитывает входные публичные IP, а не буквально телефоны/компьютеры.
Один аппарат при смене/множественных VPN-выходах может использовать больше одного
источника; несколько устройств за общим стабильным выходом могут выглядеть одним.
Время освобождения слотов и точная семантика числа в кабинете не установлены.
Не прогонять постоянный ISP-healthcheck через весь пул: он сам может занять слоты.
Наблюдение разных выходов Blanc на Cloudflare не доказывает, что именно видит ISP.

## Полнота маршрутов и пределы схемы

Домены плюс официальные голосовые IP покрывают известные маршруты. Общие CDN
целиком не включаем: это отправило бы посторонние сайты через AI-ISP. Новый
неизвестный адрес сервиса может попасть в OTHER. Fail-closed защищает трафик,
который уже совпал с AI-правилами; это не абсолютная классификация всех будущих
соединений приложения. Не обещать «весь OpenAI навсегда» по одному снимку списка.

Голосовой список обновляется при сборке. Публикация старого файла не обновит его
сама: нужны новая сборка, публикация и Update на устройствах. Системный fallback
DNS сохранён; полная изоляция DNS не доказана. Проблемный DoT из базы удалён,
проверка TLS не отключалась. Профиль не обещает обход любых блокировок во всех сетях.

## Управление, обновление и откат

Рабочая инструкция: [personal/README.md](../../personal/README.md).

| Действие | Где менять |
|---|---|
| Состав и порядок входов | personal/artme.json: servers, rotation.priority |
| Выбор входа по умолчанию | rotation.selected; затем проверить сохранённый выбор в UI |
| Другой ISP для одной категории | personal/secrets.local.json и routes.OPENAI/CLAUDE.exit |
| Правила/DNS | корневой artme.conf — база сборки; Zoom — rules/zoom.list |
| Сборка/публикация | tools/assemble_artme.py; проверка — tools/validate_artme.py |
| Персональная ссылка | локальный out/artme-url.txt |

Правка Git-исходников не равна обновлению устройства. Последовательность:
источники → сборка → проверка отдельной копии → публикация → Config Update →
Use Config → проверка выбора групп и маршрутов. Global Routing должен быть Config;
Proxy обходит выборочные правила. Для GEOIP,RU нужна Country-база.

Проверочные адреса: api.ipify.org → OPENAI, icanhazip.com → CLAUDE,
checkip.amazonaws.com → OTHER, ifconfig.me/ip → DIRECT. После смены входа первые
два должны сохранить ISP-IP; сравнивать новые соединения без браузерного кэша.
IP-страница доказывает только свой маршрут. Для DIRECT учитывать возможный
Private Relay браузера. Затем проверять текст, файлы и голос, при проблеме — журнал.

Для отката сохранить прежний Config и выбрать его → Use Config. Перед публикацией
сборщик сохраняет out/publication-before.private.json; это копия непосредственно
предыдущей публикации, при следующей публикации она перезаписывается. Важные
релизы надо сохранять отдельным снимком. Не удалять старые рабочие профили до
приёмки новых. Не восстанавливать старый файл вслепую: проверить его реквизиты,
версию клиента и соответствие текущим правилам.

Персональная публикация — secret Gist. Пользователь осознанно разрешил этот
механизм: случайный URL практически не угадывается, но любой его обладатель
может получить все VPN/ISP-реквизиты. Относиться к ссылке как к паролю. Ссылка
семьи отдельная; полные файлы, ссылки и логи не коммитятся в публичный Git.
