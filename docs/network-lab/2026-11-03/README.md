# Shadowrocket VPN и ISP итоги сессии 3 ноября 2026

Цель — сохранить один выходной IP для OpenAI и Claude на Mac и iPhone, независимо от смены входного VPN, и управлять настройкой из файлов. Цепочка подтверждена экспериментами, но автоматическая переносимость, полнота выборочных маршрутов и устойчивое качество связи ещё требуют работы. Часовой пояс журналов — Asia/Novosibirsk, UTC+7.

Разделы до «Дополнение» фиксируют первоначальные эксперименты. Текущие изменения и следующий шаг — в дополнении внизу и в `personal/README.md`.

## Требования и решения

- Клиент — Shadowrocket на Mac, iPhone и в перспективе iPad.
- OpenAI и Claude имеют независимые группы и ISP-выходы; пока можно использовать один адрес для обеих групп.
- В последней согласованной схеме остальной PROXY идёт через входной VPN. Прежнее решение отправлять весь PROXY через ISP пересмотрено ради расхода трафика и скорости.
- DIRECT-исключения сохраняются: локальные сети, российские IP, Zoom, Slack и другие существующие правила.
- Для трафика, попавшего в AI-группы, нет запасного выхода с другим IP. При отказе цепочки соединение должно прекращаться.
- Отдельная семейная подписка содержит только серверы; персональный профиль содержит правила и цепочки. Семейную публикацию в этих экспериментах не меняли.
- Разовая настройка на устройстве допустима, но полное управление из файлов остаётся желаемым результатом.

Полный контекст с приватной ссылкой и соответствием адресов находится в `out/network-lab/2026-11-03/CURRENT_STATE.md`. Не брать адрес из имени файла или старого сообщения как доказательство текущего провайдера.

Первый полный персональный `artme.conf` был опубликован до сетевой проверки и оказался неработоспособен из-за привязки цепочки. На момент первоначального сохранения основной сборщик ещё содержал неподтверждённый механизм `chain=ENTRY-*`. Позднее он переработан; текущий статус описан в дополнении ниже и в `personal/README.md`.

Последний присланный телефонный лог заканчивает сравнение в режиме **Proxy**, где ISP обходится. Это историческое наблюдение, не утверждение о текущем положении переключателя. На Mac в ходе последних изолированных тестов профиль не переключали.

## Голос и маршруты

Изначально доменные правила OpenAI покрывали сайт и API, но голосовые UDP-соединения к IP-адресам попадали в общий VPN. Поэтому ранняя работа голоса в Config **не доказывала работу голоса через ISP**.

Добавлены 402 префикса из официального `chatgpt-voice.json`, версия списка от 27 октября 2026. Все 10 голосовых IP, найденных в первых сравниваемых журналах, покрыты этим списком. Последующие телефонные логи подтверждают применение IP-правил группы OpenAI.

OpenAI описывает UDP/3478 как предпочтительный голосовой транспорт и допускает TCP/443 при недоступном UDP. Для Proxy-Seller пользователь подтвердил работоспособность голоса, но качество аудио и выбранный медиатранспорт нельзя полностью восстановить только из VPN Logs.

Официальные домены покрываем вместе с поддоменами; голосовые IP берём из опубликованного списка. Нельзя направлять целиком общие диапазоны Microsoft или Cloudflare в AI-группы. Неизвестный новый адрес сервиса сейчас попадёт в обычный VPN: выборочная схема не даёт абсолютной гарантии единого IP для любого будущего соединения OpenAI. Для такой гарантии всему внешнему трафику устройства нужен единый выход, с отдельно согласованными DIRECT-исключениями.

Автоматическое обновление голосового списка ещё не реализовано: опубликован снимок. Статическая проверка списка не заменяет сценарные проверки входа, файлов, голоса, видео и долгих соединений.

## Переносимость и привязка цепочки

На Mac подтверждён вариант `chain=<внутренний UUID входного узла Shadowrocket>`. Привязки по имени узла/группы не дали надёжного результата. Параметр `underlying-proxy` в экспериментах игнорировался и мог создавать ложное впечатление работающей цепочки.

В телефонном профиле все входные серверы, ISP-узлы и правила уже содержатся в файле. После импорта пользователь один раз задаёт **Proxy Pass** у `PHONE-ISP-OPENAI` и `PHONE-ISP-CLAUDE`, выбирая реальный входной сервер на этом устройстве. До привязки используется намеренно отсутствующий родитель; `close-if-proxy-chain-missing = true` должен блокировать AI-соединения.

Выбор сервера в `PHONE-BASELINE` не меняет родителя ISP. После обновления профиля привязки нужно проверять заново. Поведение сохранения локальных привязок при автоматических обновлениях ещё не подтверждено.

Имена экспериментальных узлов должны быть уникальны: Shadowrocket использует общий реестр серверов. Повторные имена между импортированными профилями уже исказили ранние результаты; эти выводы были пересмотрены.

## Что означает Multi-device access IPRoyal

По документации ограничиваются одновременно используемые **входные публичные IP**, а не вкладки, группы или число соединений. Несколько устройств за одним стабильным VPN-выходом могут выглядеть как один источник. Одно устройство через VPN с несколькими выходами может задействовать несколько источников.

Время освобождения места после последнего соединения или размер возможного временного окна в изученной документации не раскрыты. Значение «4» в кабинете предположительно означает один базовый и три дополнительных источника; точную семантику поля нужно подтвердить у IPRoyal.

Связь отказов прежнего IPRoyal с меняющимися входами Blanc — сильная рабочая гипотеза, не подтверждённая провайдером причина. Новый адрес одновременно отличается и планом, и самим IP, поэтому удачный новый тест не изолирует влияние только доплаты.

## Скорость нового IPRoyal

Изолированные sing-box процессы, одна TCP-сессия на загрузку, последовательно через четыре маршрута. Сервис — измерительный endpoint Cloudflare Speed Test. На каждый маршрут скачаны 10 + 10 + 5 МБ, всего 100 000 000 байт. Порядок VPN/цепочки чередовался. Запросы по 12,5 МБ сервер сначала отклонил с HTTP 403; эти ответы исключены из измерений.

| Маршрут | Медиана полной загрузки Мбит/с | Первый байт нового соединения, с | Повторный запрос по открытому соединению, с |
|---|---:|---:|---:|
| Blanc | 15,68 | 1,103 | 0,273 |
| Blanc → новый IPRoyal | 5,23 | 2,501 | 0,412 |
| Xeovo New York | 16,79 | 0,988 | 0,215 |
| Xeovo New York → новый IPRoyal | 11,31 | 2,205 | 0,352 |

Дополнительная задержка повторного маленького запроса составила около 140 мс; это HTTP TTFB, не ping и не время генерации модели. Отдельно замечен серьёзный провал: 5 МБ через Xeovo → ISP загружались 91,041 секунды. Две предыдущие загрузки по 10 МБ на этом маршруте занимали 3,671 и 7,076 секунды.

Тест относится к одному вечеру и одной площадке. Cloudflare выбирал разные площадки для разных выходов. Он не измеряет upload, потери UDP или качество аудио и не устанавливает виновника замедления. Новый IPRoyal пока нельзя считать стабильно быстрым только по отсутствию отказов подключения.

## Следующие шаги

1. Уточнить у IPRoyal окно учёта входных IP, освобождение мест, точный смысл значения Multi-device access и допустимость частой смены входа VPN.
2. Повторить сравнение скорости на второй площадке и в другое время. Сохранить также плохие результаты; проверить upload и задержку/потери под нагрузкой для оценки голоса.
3. Если новый IPRoyal выбран для следующей телефонной пробы, явно заменить его в тестовой публикации. Сейчас опубликован прежний адрес. На Mac ничего автоматически не переключать.
4. Проверить новый IPRoyal с UDP в нативном Shadowrocket на iPhone: IP-страницы, текст, файлы, голос несколько минут; затем проверить фактические маршруты в журнале.
5. Исправить или заново импортировать Xeovo на iPhone и проверить WebSocket-параметры. Успех в sing-box не считать подтверждением нативного формата.
6. Реализовать проверяемую сборку и обновление официальных правил; отдельно решить переносимость родителя ISP и сохранение привязки при обновлении.
7. Только после этого выпускать финальный персональный профиль и возвращаться к watcher/kill switch с корректным ожидаемым выходом.
